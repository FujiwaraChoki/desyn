Designs never change except through **transactions**: an ordered list of **operations** with an id, a label and a source. The editor, collaborators, the AI, workflows, imports and the Agent API all use the same operations, which is why every change is live, undoable and attributable.

## Operations

<Generated name="model-types" names="Op" />

| Op | Use it to |
| --- | --- |
| `create` | Insert a subtree. `nodes[0]` is the subtree root (its `parent` is overwritten with `parent`); the other nodes are its descendants. All ids must be new. `index` positions it among the parent's children (omitted = top). |
| `update` | Shallow merge of top-level properties with `set`, removal with `unset`. Nested values are replaced whole. Cannot change `id`, `type`, `parent` or `children`. |
| `patch` | Deep set at a path, for fine edits such as `["layout", "gap"]` or `["style", "fills", 0, "color"]`. |
| `delete` | Remove a node and its subtree. If the node is already gone, the op is dropped as `missing-node` and nothing changes. |
| `move` | Reparent or reorder. `index` is the node's **final** position, counted after it is removed from its old place; omitted = top (end of `children`). Position is not adjusted, so `x`/`y` stay relative to whichever parent the node ends up in. |
| `asset` | Add, update or remove `AssetRef`s. |
| `styles` | Deep set into `Design.styles` (colors, text styles, effect sets, variables). |
| `doc` | Change the design's name, kind, brand kit or meta; `unset: ["brandKitId"]` detaches the brand kit. |

## Transactions

<Generated name="model-types" names="Transaction" />

`id` is generated by the client and is the idempotency key: committing the same transaction twice has no further effect. `label` is what history shows ("Move headline", "AI: make it more premium"). `actor.runId` ties AI and workflow transactions to their run so clients can group them into one undo step.

## Examples

```json
{
  "id": "tx1a2b3c4d5e",
  "label": "Warmer headline",
  "source": "user",
  "ts": 1792483260000,
  "ops": [
    { "op": "patch", "id": "h1a2b3c4d5e6", "path": ["style", "fills", 0, "color"], "value": "#ffb02e" },
```

## Dropped ops

`applyTransaction` never throws on bad input. An op that references a missing node or parent, would create a cycle, or would break an [invariant](/developers/document-model#invariants) is skipped and reported:

```json
{
  "applied": [{ "op": "update", "id": "h1a2b3c4d5e6", "set": { "name": "Headline" } }],
  "dropped": [{ "index": 0, "reason": "missing-node" }]
}
```

The reason is one of a fixed vocabulary (`DropReason` in `@desyn/schema`, specified with the check order for every op in `spec/fixtures/README.md`):

| Reason | The op… |
| --- | --- |
| `invalid-op` | is malformed: unknown `op`, missing or ill-typed fields, a key in both `set` and `unset`, or a `doc` change to an unknown field |
| `missing-node` | targets a node (`update`, `patch`, `delete`, `move`) that does not exist |
| `missing-parent` | names a `create` or `move` parent that does not exist |
| `not-container` | puts children into a node that is not a root, page, frame, group or boolean |
| `cycle` | moves a node into itself or one of its descendants |
| `duplicate-id` | creates a node whose id already exists, repeats within the op, or is `"root"` |
| `immutable-field` | uses `update` or `patch` on `id`, `type`, `parent` or `children` |
| `invalid-node` | produces a node that fails validation, or creates a structurally inconsistent subtree |
| `root-protected` | deletes or moves the root, or creates another root |
| `page-nesting` | places a page anywhere but directly under the root, or anything else directly under the root |
| `invalid-path` | patches an empty path or a path that does not resolve |
| `invalid-value` | sets an asset, styles or `doc` value of the wrong shape |

A dropped op changes nothing; the ops after it still run against the state left by the ops before it.

This matters for collaboration: by the time your transaction reaches the server, someone may have deleted the node you edited. Your other ops still apply.

## Undo

Applying a transaction also returns its **inverse**, a transaction that restores the previous state exactly. Undo applies the inverse; redo re-applies the original. Each transaction is one undo step.

## In TypeScript

`@desyn/doc-ops` implements the same semantics as the Rust core (verified by shared conformance fixtures in `spec/fixtures/`), and includes builders for common edits:

```ts
import { applyTransaction, makeTransaction } from "@desyn/doc-ops";

const tx = makeTransaction(
  [{ op: "patch", id: "h1a2b3c4d5e6", path: ["style", "fontSize"], value: 112 }],
  "Bigger headline",
  { source: "ai", actor: { agent: "my-agent" } },
);
const { design: next, inverse, applied, dropped } = applyTransaction(design, tx);
```

TypeScript appliers used by Convex apply ops verbatim and do not run layout; they trust the derived geometry (text boxes, auto-layout positions) the client included in the same transaction. The Rust core and the render worker run layout after every transaction.
